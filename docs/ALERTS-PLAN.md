## Slice F1: findings foundation (schema v14; v13 is the N2 index; if N2 needs no index, F1 is v13 and F2 is v14)

- **Memory (repositories):** `FindingRepository` (`record`, `open`, `by_id`, `update_status`, `counts`), `ExpectationRepository` (`add`, `remove`, `list`, `matching(kind, subject)`), `DetectionState` (learning start, per-detector watermark).

Additive, permanent (the purge of detail never touches them). Written only by the service.

## Slice F2: things that are NEW (rules, no statistics)
Each rule is a pure function with a one-sentence "why" and the evidence it used.
| Rule | Fires when | Tier |
|---|---|---|
| New program | an executable first seen after the switch-on moment, no known product covers it, and it is NOT an update: a new path with the same signer in the same program group or known-product folder (self-updating apps put each version in a new folder) is recorded as an update, not raised | unusual; suspicious when unsigned, or in a user-writable folder (Temp, Downloads, AppData) |
| New start entry | a launch record (service, task, Run key, Startup file) first seen after the learning period | unusual; suspicious when its target is unsigned or user-writable |
| Changed file | the same path now has a different SHA-256 AND (signer changed, or signed became unsigned) | suspicious (same signer, new version: not a finding; recorded as an update) |
| New account | a program runs as an account it never used (for example SYSTEM) | unusual |
| New owner for a program | a program talks to a network owner it never did (needs owner data; otherwise the rule is off and says so) | unusual |
`Changed file` needs the identity facts of the previous inspection: a small `identity_history` table (path id, sha256, signer, status, seen_at; additive, schema v15) because `executable_identity` keeps only the latest row.
Tests first: one table-driven test per rule (fires, does not fire, covered by an expectation, before the switch-on moment, an update path of the same signer and group).

## Slice F3: USAGE above what is expected
Explainable statistics only (docs/PLAN.md decision 7), no machine learning.
- Per program and per hour, from `rollup_process_hour` and `rollup_traffic_hour`: CPU average, memory peak, bytes sent, bytes received. The system as a whole from `rollup_system_hour`.
- Baseline per program and metric: the 95th percentile and the maximum of its own hours in the last 14 days, leaving out hours that raised a finding; it needs at least 48 active hours before it is trusted ("not enough history" otherwise, shown, never guessed).
- A finding needs ALL of: above max(3 x the 95th percentile, 1.5 x the prior maximum), above an absolute floor (for example 100 MB sent in an hour, 25% CPU, 500 MB more memory), and sustained for 2 consecutive hours (a single hour only for bytes sent above 10 x the prior maximum, the exfiltration shape).
- The sentence says it in numbers: "Sent 2.1 GB in the hour from 14:00. In the 14 days before, its busiest hour was 310 MB and 95% of hours were under 120 MB."
- Buttons: Expected this time; Raise the limit to this level (stored as an expectation with the new ceiling); Not expected.
- All numbers are in `config/service.toml` (floors, multipliers, window, history needed).
- Covers per program: CPU, memory, bytes sent and bytes received. NOT disk per program: the stored per-program hourly rollup has no I/O columns (and "disk" here would only mean file I/O, not the physical disk anyway); disk exists only for the machine as a whole, so a machine-wide disk finding is the only disk alert possible, and per-program disk would need a new collection and rollup first.
- Known limit: no time-of-day or day-of-week pattern in v1 (a backup that runs every night is learned as "its busiest hour is high"); a seasonal baseline is a later slice if the backtest shows it is needed.

## Slice F5: known patterns of rogue software (approved 2026-11-17; F5a and F5b BUILT, see docs/PATTERNS.md; F5c skipped by the user)
The user asked whether SYNTRAC can use known patterns of shady or rogue programs to identify them. Yes, as a fixed, reviewable set of rules that SYNTRAC ships with (no download at run time, nothing leaves the machine), each tied to a public technique name, and each limited to what SYNTRAC already records. They raise findings through the F1 machinery (same buttons, same expectations, same "why"), at most at the tier "suspicious": a pattern match is a reason to look, never a verdict.

**Where the patterns come from (checked 2026-11-16):**
- The technique catalogue of MITRE ATT&CK: free to use for research, development and commercial purposes if MITRE's copyright notice and licence are reproduced; no use of the name that implies endorsement. Each SYNTRAC rule cites its technique id (for example T1036.005, "masquerading: match legitimate name or location") as a label only, with the notice in `docs/`.
- SigmaHQ rules (licence DRL 1.1: use allowed with credit to the rule author wherever matches are shown) and the LOLBAS list (GPL-3.0, which would bind the whole project if bundled): their FILES are NOT copied. They are read as references for what is worth looking for, and each SYNTRAC rule is written from scratch against SYNTRAC's own data. Where a rule is directly inspired by one, the rule text names it.
- The rules cannot be a downloaded feed: the "no network except the one owner-data download" rule stays.

**Closed vocabulary, no scripting:** a rule is a small data entry (`config/patterns/*.toml`, embedded in the build) with an id, title, technique id, tier, a plain "why" and "benign reasons" text, and conditions chosen from a fixed list evaluated by pure code: name equals or within one edit of a list, folder under or not under a list of folders, signature state, signer in or not in a list, double extension, parent name, start-entry kind, "first network use", "first time as this account". No regular expressions over user data, no code in rules, so a rule cannot be made slow or hostile. A rule pack has a version, shown on the Findings tab.

**Starter patterns (each only if SYNTRAC records what it needs):**
| Pattern | Data used | Notes |
|---|---|---|
| A system program name running from the wrong folder (svchost, lsass, csrss, services, winlogon, explorer, taskhostw ... outside System32 or the Windows folder), or a name one letter away from one (svch0st, scvhost) | executables path, identity | T1036.005, T1036.004. Strong and quiet |
| An unsigned program (or one with no company) running from Temp, Downloads, a user's AppData, Public or the root of ProgramData | path, identity | T1204, T1036. Quiet once known products exist |
| A start entry (service, task, Run key, Startup file) whose target is unsigned, or lives in a user-writable folder | launch records, identity | T1547.001, T1053.005, T1543.003 |
| A double extension or a document name ending in an executable one (invoice.pdf.exe), or a name with direction-override characters | path | T1036.007, T1036.002 |
| Script and download helpers (powershell, wscript, cscript, mshta, regsvr32, rundll32, certutil, bitsadmin, msiexec) using the network for the FIRST time, or from a new parent | rollups; processes (parent, 30 days raw) | T1218, T1105, T1059. Only "first time", because each also has normal uses |
| An office or browser program starting a command shell or a script host | processes (parent, command line, 30 days raw) | T1566, T1059. Needs the raw rows, so it can only look back 30 days |
| Regular, clock-like connections from one program to one destination (a beacon): at least 10 connections whose gaps vary by under 10% | raw flows (30 days) | T1071. Gated: the program is new, unsigned or unknown, and the destination is new; the backtest decides if it is usable at all |
| Dual-use tools that appear: remote access (AnyDesk, TeamViewer, RustDesk, ScreenConnect ...), tunnels (ngrok, cloudflared, frp, chisel), bulk copy to the cloud (rclone) | name, signer, company | T1219, T1572, T1567. "Commonly used by attackers and by administrators"; unsigned or in a user-writable folder is higher. Named so the user can confirm in one click, like Acme |
| A hash from a list the USER imports (F5c) | SHA-256 in identity | The only route to the tier "confirmed". A file the user downloads and imports by hand (for example a public hash list), never fetched by SYNTRAC; its source and licence are the user's choice, shown with each match |

**Honest limits:** names, folders and signers are weak evidence on their own (anyone can name a file anything, or sign with a stolen certificate), and a patient program that avoids every pattern will not match. The value is catching the careless majority and giving the user a short, explained list. Every pattern states its likely harmless explanation. Patterns that need raw processes or flows see only the last 30 days.

**Slices:** F5a the pattern engine and the path/name/signature/start-entry patterns (everything from tables SYNTRAC already keeps); F5b parent-child and first-network-use patterns; F5c the hash-list import and the beacon pattern (the beacon only after the backtest). Tests first: each pattern in a table-driven test (matches; harmless look-alike does not; covered by an expectation; Known product does not match); the vocabulary parser (unknown condition is refused at build time); the name-distance function; the backtest prints how many of today's programs each pattern matches, and the list is read by the user before anything is enabled (`patterns_enabled = false` until then).

## Slice F6: a tighter "whole folder" (approved 2026-11-17; BUILT 2026-11-17, see aiChangeLog/phase-F6.md)
**Problem.** "Always expected for the whole folder" (and "Mark as expected" on the review screen) covers every FUTURE `new_program` finding below a folder. For a folder an ordinary program can write to, that lets a rogue program copy itself in and never be called new. Other kinds (start entries, changed files, network owners, usage, every pattern) are separate kinds and are still raised; only "this is a new program" is silenced.

**Rule.** A folder is **protected** when it is under `Windows` or `Program Files` / `Program Files (x86)` ON THE WINDOWS DRIVE and not inside one of a short, fixed list of folders ordinary users can write to anyway (`Windows\Temp`, `Windows\Tasks`, `Windows\Tracing`, `System32\Tasks`, `SysWOW64\Tasks`, `System32\spool\drivers\color`, `Registration\CRMLog`, `Debug\WIA`, `...\MachineKeys` and the like; checked with read-only `icacls` on a real machine). Everything else (another drive, ProgramData, a profile, Temp, a network share) is **writable**. The check reads the path text only; an application's own writable subfolder inside `Program Files` (a log folder) cannot be known and is a documented residual.
1. A whole-folder expectation (`folder:`) can only be CREATED for a protected folder: by the Findings button and by the review screen. The service refuses otherwise, whatever the client sends.
2. MATCHING: a `folder:` expectation whose root is protected covers a program only if the program's own path is protected too (so `folder:c:\windows` no longer covers `Windows\Temp\x.exe`).
3. Review screen, writable group: the button becomes "Mark these N programs as expected". It stores one expectation per program of that group, exactly those the screen showed (seen before the switch-on, no known product, no expectation), and refuses the whole request if there are more than 500.
4. Expectations that already exist for writable folders are kept and still honoured; the list "What you told SYNTRAC is expected" marks each with a warning and a one-click remove. Nothing is deleted or switched off by the build.
5. **Build folder (the one deliberate exception).** From a `new_program` finding in a writable folder the user may choose "Expect new programs in this build folder". It stores `build:<folder>`, covers ONLY the `new_program` kind, is never allowed in Temp (subfolders included), Downloads, Desktop, Documents, a profile root, a drive root or a network share, is never created from the review screen, and every program it hides is still recorded and counted in the Findings digest ("N new programs in your build folders in the last day").
Tests first: the protection rule on a table of paths, creation refused, matching narrowed, the review batch (exactly the shown set, cap, refusal), the build-folder rules, the digest count, the contract suites unchanged (no schema change). A backtest on a copy of the live data counts how many programs that are suppressed today the matching change would raise, and that number goes in the change log.

## Slice G: GPU use per program (approved 2026-11-20; the user wants BOTH G1 and G2 ready now, and the simple "busiest engine across all adapters" figure; G1 and G2 BUILT, see aiChangeLog/phase-G1.md and phase-G2.md)
**Problem.** SYNTRAC records CPU, memory and network per program but nothing about the GPU. A rogue program (a miner, a password cracker) can do its work on the GPU and look idle on the CPU. It would also fall into the "others" tail, because the per-sample top list is chosen by CPU.

**Data source (checked read-only on the user's machine 2026-11-20).** The Windows performance counters `GPU Engine(*)\Utilization Percentage` and `GPU Process Memory(*)\Dedicated Usage` answer per process: 1,154 engine instances and 77 memory instances were present on a machine with three adapters. Each instance name carries the process id, the adapter, the engine number and the engine type (3D, Compute, Copy, VideoDecode ...). `sysinfo` has nothing for this; the `windows` crate already used gets one more feature flag (`Win32_System_Performance`), so no new package. A machine, driver or virtual machine without the counters is recorded as "not available", never as 0.

### G1: capture (schema v16, additive)
- **Definition (one unit, written in the code and the docs).** A process's GPU figure is the percentage of its BUSIEST ENGINE, the way Task Manager shows it: instances of one process that are the same engine (several contexts) are added, then the highest engine over ALL adapters is taken. It is a share of one engine, NOT of "the whole machine", so it is never divided by the core count. GPU memory is the process's dedicated GPU memory, summed over adapters (shared system memory is not counted).
- **Core.** `ProcessMetric` gets `gpu_percent: f32` and `gpu_memory_bytes: u64`; `SystemMetrics` gets `gpu_percent: Option<f32>` (None = not available); `OtherProcesses` gets `gpu_percent` (the largest single value in the tail) and `gpu_memory_bytes` (the sum). A pure `parse_gpu_instance(name)` and a pure `gpu_by_process(rows)` turn counter rows into per-process figures. `build_sample` takes the GPU figures as an input and lists the UNION of the top N by CPU and the top 5 by GPU (GPU at or above 1%), so a program heavy on the GPU and light on the CPU is listed by name.
- **Ports.** A `GpuSource` trait (returns the counter rows or "not available") with a fake for tests; the Windows adapter (`gpu_counters.rs`) reads the counters; `SysinfoMetricsSource` receives it by injection. A service switch `gpu_metrics_enabled` (default true; capture is passive and local). **Cost check first:** a read-only example measures one wildcard read on this machine; if it costs more than about 5% of one core at the 5-second cadence, the GPU is read every third sample and the value carried between reads, and that decision goes in the change log.
- **Store.** Migration 16, additive `ALTER TABLE ... ADD COLUMN` with defaults: `process_metrics` (gpu_percent, gpu_memory), `system_metrics` (gpu_percent NULL when not available, others_gpu_percent, others_gpu_memory), `rollup_process_hour` (gpu_avg, gpu_peak, gpu_memory_peak), `rollup_system_hour` (gpu_avg, gpu_max). Hours already rolled up keep 0, which the detector reads as "no GPU data" (an inactive hour). The rollup build stays deterministic (same fixed order of sums as CPU); the migration test checks that a v15 database keeps all its data.
- **App.** Programs history and Program detail get "GPU (peak)" and "GPU memory (peak)", sortable like the other columns; the overview shows a system GPU line only when the data is available. No new screen.
- **Tests first.** Instance-name parsing on a table of real-looking names (including several contexts of one engine, an adapter id, a name that does not parse); per-process figures (busiest engine, memory sum, two adapters, a process that disappears); `build_sample` (the union list, the tail, "not available"); the store contract suites on both stores (write, read back, rollup); the v16 migration test; the fake source in a collector test; the app views and the sort.

### G2: detection (no schema change; on by the same switches as before)
- **Usage rule (`usage.rs`).** Two new metrics, GPU (the hour's average) and GPU memory (the hour's peak), judged exactly like CPU and memory: against the program's OWN earlier active hours, above `max(3 x p95, 1.5 x highest)`, over a floor (GPU 20% of an engine, memory 500 MB above the highest peak), sustained for the last two hours. The same expectation ceiling and the same "hours already flagged are left out" apply. **Honest limit:** a program needs 48 active GPU hours before it is judged, and a brand-new miner has none, so this rule mostly catches a KNOWN program that suddenly computes (a browser, an updater, a service). The next rule covers the new one.
- **New pattern condition `sustained_gpu = { percent, hours }` (pack 2026.11.3).** The program's hourly GPU average was at least `percent` in each of the last `hours` completed hours. It needs no history, so it can judge a new program. One pattern uses it: **"An unsigned program in a user-writable folder keeps the GPU busy"** (signature unsigned/untrusted/altered, location user_profile/temporary/program_data/network, 30% for 3 hours in a row, tier unusual and NOT lifted: unsigned in a writable folder is already the condition, so a lift would make every match suspicious; see phase-G2). Its harmless explanation is written in the pattern: games, renderers, local AI tools and unsigned tools you built yourself. The vocabulary stays closed: an unknown condition still stops the pack from loading.
- **Reads.** `ProcessHourRow` gets the two GPU values; the pattern reuses `UsageRepository` (no new port), under its contract suite on both stores.
- **Tests first.** Usage: a steady GPU user is silent, a sudden jump raises one finding with the numbers in the sentence, a floor, one hour is not enough, a flagged spell stays out of the baseline, a zero-history program is not judged. Pattern: the parser accepts `sustained_gpu` and refuses a bad value; a synthetic three-hour miner series matches; a signed program, a short burst and a covered (expected) program do not; the pack version is shown.
- **Backtest.** `rehearse_detect` gets a GPU section. Today's data has no GPU history, so it says so; the G2 tests use synthetic series, which is what "ready now, useful later" means. After about two weeks of capture the section is run again on a copy and read by the user before anything is relied on. The user runs local AI on the GPU, so that program is expected to match once and be marked expected.

**Order.** G1 (measure, then tests, then code, one commit, one `verify.ps1`), then G2 (the same). A service reinstall and an app rebuild are needed together for G1 (new schema, new pipe fields). No new dependency, no network.

**Limits.** In-browser mining (WebGL or WebGPU) is attributed to the browser, so it shows as "the browser used the GPU more than usual". A GPU in a mode the counters do not cover shows nothing. Per-adapter temperature, power and clock speed are out of scope. Utilisation is what the driver reports for each engine; a very short burst between two samples can be missed.


## Slice T: tray helper (approved 2026-11-20 with the single-instance plugin; T1 and T2 BUILT, see aiChangeLog/phase-T1.md and phase-T2.md)
**Today.** Toasts are planned in the web page (`planToasts`, `useToasts`, fed by the findings poll in `App.tsx`) and the on/off switch lives in `localStorage`. Closing the window ends the process, so alerts stop with it. A second launch opens a second app.

**Options.** (A) Keep the window hidden and let the page keep polling: smallest, but a whole web view stays resident (a hundred MB or more) and alerts depend on a hidden page's timers. (B) The SAME program keeps running with NO window, and a small background watcher in Rust sends the toasts. (C) A separate helper program: a second thing to install, update and keep in step. (D) The service sends the toasts: impossible, a SYSTEM service has no desktop to show them on. **Recommendation: B**, in two slices.

### T1: tray, close-to-tray, alerts without a window
- A tray icon (Tauri's `tray-icon` feature; its packages are already in the lock file, a lock diff will confirm there is nothing new). Menu: Open SYNTRAC, Findings (N open), Notifications on/off, Quit. Left click opens the window. Tooltip: "SYNTRAC: N open findings" or "SYNTRAC: the collector is not running".
- Closing the window DESTROYS it (the web view's memory is freed) and the program keeps running in the tray; Open creates it again. Only Quit ends the program.
- **A watcher in Rust** reads the open findings from the database every 30 seconds (the same view the Findings tab uses) and sends the toasts through the notification plugin's Rust side. `planToasts` is ported to Rust with the same rules and the same tests (one toast for each new suspicious finding, at most three; unusual ones as one summary; the digest never). The page stops sending toasts, so there is exactly one sender.
- **Findings raised while the program was not running** are announced once at the next start, as a summary: the last announced finding id is kept in a small settings file, so a 3 a.m. finding is not lost. The very first run ever announces nothing (what is open is not news).
- The Notifications switch moves from `localStorage` to that settings file (`%APPDATA%\SYNTRAC\app.json`; a missing or damaged file means the defaults), and the sidebar button and the tray item both use it.
- **One instance only**: a second launch opens the window of the running one. Recommended with the official `tauri-plugin-single-instance` (small); the alternative is a named mutex written by hand.
- Tests first: the toast plan (the existing cases), the watcher's decision (first run, announce only ids above the last announced, off switch, a cap), the tray menu and tooltip text, the settings file (round trip, damaged file). The window and tray glue is checked by hand with a short checklist in the change log.

### T2: start with Windows (a separate slice because it changes the machine)
- A "Start with Windows" item in the tray menu, OFF until you turn it on. It writes one value under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` (no administrator rights) that starts the program with `--tray` (no window); turning it off deletes that value. Written through a small trait with a fake for tests (the real one is a few lines over the registry).

**Limits.** A toast from a program that is not installed through an installer may show under another name, and clicking it may not open SYNTRAC (the notification plugin offers no click action on Windows): the tray icon is the way in. If the program is killed or the PC is off, nothing is announced until the next start (then the summary above). Toasts say "unusual" and "suspicious", never "malicious".
**Out of scope.** Toast buttons, sound, a tray program that outlives the app, mail or phone delivery.
## Backtest before anything is switched on (applies to F2, F3, F4 and F5)
`crates/syntrac-store/examples/rehearse_detect.rs`: on a COPY of the real database, replays the last 30 days hour by hour through the same pure rules and prints how many findings each rule would have raised, the noisiest programs, and a sample of the sentences. Thresholds are tuned from this before the detect worker is enabled by default (`detect_enabled = false` until the user has read the backtest).

## Out of scope here
Threat-intel lists, YAML rule files, alert rules over command lines or parents (Phase 3 proper), the LLM "Investigate" button (Phase 4), a tray helper (WANTED LATER: see decision 8), mail or phone delivery, and any use of the network.

## Honest limits
- A rogue program that behaves normally for a week becomes part of the baseline: that is why the review screen and the "new start entry" and "changed file" rules matter more than usage statistics.
- A finding is evidence, never a verdict. "Expected" means "the user said so", and the screen shows who said it and when.
- If the service is stopped, nothing is detected; the existing "collector offline" banner stays the signal for that.

## Order and size
S1 (small) -> N1, N2 (small each) -> F1 (largest: schema, ports, pipe, tab) -> F2 -> backtest -> F3 -> F4 -> F5 (after its own approval). Each slice ends with `verify.ps1` green, a rehearsal on a copy of the live data, a change log in `aiChangeLog/`, doc updates, and a commit. Push in batches.
