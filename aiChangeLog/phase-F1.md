# Phase F1: findings foundation (schema v13)

Slice F1 of `docs/ALERTS-PLAN.md` (approved 2026-11-16). Findings that the user can teach: what a detection rule found, what the user decided, what they said is expected. No detection rule ships in this step; F2 adds the "new thing" rules and F3 the usage rules, so a rebuilt service with `detect_enabled = true` would store nothing yet.

## What changed
- **Core (pure).** `findings.rs`: `Candidate`, `Finding`, `Expectation`, `Tier` (unusual, suspicious, confirmed), `FindingStatus`; `reconcile` (an expectation for the same kind and exactly the same subject drops a candidate; a candidate already stored is touched, left alone (expected), left alone until its snooze ends, or reopened (resolved) by its status; the rest are inserted most serious first up to `max_new`, the overflow counted); `apply_decision` (expected this time, always expected which also yields an expectation built from the finding's own kind and subject, not expected, snooze of 1 to 365 days, reopen; notes cleaned and capped at 200 characters). `findings_run.rs`: the ports `FindingRepository`, `ExpectationRepository`, `DetectionStateRepository`, the `Detector` trait, `clean_candidate`, and `run_detection` (switches detection on at the first run, asks every detector, a failing detector is reported and never stops the others, reconciles, writes in one transaction, records the run).
- **Stores.** Migration 13 (additive, no backup): `findings` (dedupe key UNIQUE), `expectations` (UNIQUE per kind and subject), `detect_state`. SQLite and in-memory implementations pass one shared contract suite (`findings_contract.rs`), which also runs whole detection runs through the repositories. A write batch is one transaction.
- **Pipe.** `Request::FindingDecide { id, decision, days, note }` and `ExpectationRemove { id }`. Service: `FindingsAdmin` / `FindingsControl` (checks the decision, loads the finding it stored, stores the expectation first so nothing is half done, logs each change); `ServiceHandler::with_findings`; the findings commands work whether or not the detect worker runs.
- **Detect worker.** `detect_worker.rs` on its own thread with its own connection (like the launch worker). Config `detect_enabled = false` (default: off until the backtest has been read), `detect_interval_minutes = 5`, `detect_max_new_per_run = 50`. `config/service.toml` documents them.
- **App.** `history_findings.rs` (read-only view: findings by status with the counts of every status, expectations, detection state), `Backend::findings`, `decide_finding`, `remove_expectation`, commands `get_findings`, `decide_finding`, `remove_expectation`.
- **Frontend.** A "Findings" tab: detection note (not run yet, or on since and last ran, with the last error), status filters with counts, a card per finding (tier as a word and a shape, why, evidence, how many times found), the decisions (expected this time, always expected with an optional note and the words "only this kind of finding about this program", not expected, snooze for 1, 7 or 30 days, reopen), and "What you told SYNTRAC is expected" with Remove after a question. The page says a finding is evidence, not a verdict.

## Tests (written first)
Core `tests/findings.rs` (18); testkit `findings_contract` (11 cases, both stores); store `migration_v13_tests.rs` (4: upgrade, survives the purge, a duplicate is refused, a failed batch changes nothing); ipc `protocol.rs` (+3); service `findings_admin.rs` (8) and `detect_worker.rs` (3); app `tests/history_findings.rs` (7); frontend `Findings.test.tsx` (21).

## Limits (as designed)
No detectors yet. An expectation covers exactly one kind and one subject (the review screen in F4 will group them). Detection stays off until the service configuration enables it; the first run is the moment "new" counts from. The service must be reinstalled with this build (schema v13) and the app rebuilt together.
