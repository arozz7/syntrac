# Phase F6: a tighter "whole folder" (no schema change, still v15)

Slice F6 of `docs/ALERTS-PLAN.md`, requested by the user on 2026-11-17 ("I worry about the this folder if something copies into a folder to run out of it?"). Plan approved with: existing writable-folder expectations KEPT but flagged (1A), and an explicit narrow "build folder" exception for developer folders (2B).

## What changed
- **Protection rule** (`syntrac-core/src/folder_protection.rs`, pure, new): `is_protected_path` (Windows or Program Files, minus a fixed data list of folders ordinary users can write to anyway), `is_protected_on_system_drive` and the folder variants (only the Windows drive counts, because a data drive's `Program Files` follows its own permissions), `system_drive()`, and `build_folder_problem` (why a writable folder may not be a build folder). The list was checked with read-only `icacls` on a real machine: `Windows\Tasks`, `Tracing`, `System32\Tasks`, `SysWOW64\Tasks`, `System32\spool\drivers\color`, `Registration\CRMLog`, `Debug\WIA` and `...\MachineKeys` are user-writable; `Windows\Temp` is a temporary folder already; a data drive's `Program Files` can be user-writable (one was, one was not): judged writable on purpose.
- **Matching** (`findings.rs`): a `folder:` expectation whose root is protected covers a program only if the program's own path is protected too (so `Windows` no longer covers `Windows\Temp\x.exe`); an older `folder:` expectation for a writable folder is still honoured.
- **Creating**: `folder_scope_of` / `apply_decision` now take the Windows drive and refuse a whole folder that is not protected, with a plain reason. New scope `build_folder` (`ExpectationScope::BuildFolder`, subject `build:<folder>`): `new_program` only, refused for Temp (subfolders too), Downloads, Desktop, Documents, a profile root, AppData itself, ProgramData itself, a drive root, a share, the Windows folder and a protected folder, and only from a finding (never from the review screen).
- **Service**: `FindingsAdmin` holds the Windows drive (set by the host from `SystemDrive`, never by a client); `confirm_review` refuses a writable folder; new pipe request `ReviewConfirmPrograms { root, publisher }` and `confirm_review_programs`: the service rebuilds the group exactly as the review shows it (`review_group_keys`: seen before the switch-on, no known product, nothing expected yet, that folder and publisher) and stores one item expectation per program, refusing the whole request when there are more than 500 or none. Added to the dispatch and to the status board's write arm.
- **App**: `FindingView.buildScope`, `ExpectationView.{scope, scopeRoot, writableWarning}`, `ReviewGroupView.wholeFolderAllowed`, `DigestView.newInBuildFolders` (programs first seen in the last day inside a build folder, counted so they are never invisible). Findings tab: the scope choice offers "Only this program" and either the whole folder (protected) or "New programs in the build folder" with an explanation; the expectations list says how wide each one is and warns on a writable whole-folder one; the review screen shows "Mark these N programs as expected" for a writable group.
- **Backtest** (`crates/syntrac-store/examples/rehearse_folders.rs`, on a COPY): of the 1,999 programs covered by an expectation on the test machine, 7 stop being covered under the new matching, all installer bundles in `Windows\Temp` (so, no flood); 1,505 programs sit inside writable folders that already have a whole-folder expectation (kept and flagged; 24 of the 65 expectations).
- Tests first: 7 for the protection rule, 10 new or changed in `tests/findings.rs` (matching, creating, build folder), 3 for `review_group_keys`, 10 new in the service tests (refusals, drive from the service, build folder, review batch exact set, limit, pipe), 4 for the app views and digest, 6 for the screens. The contract suites are unchanged (no schema change).

## Deviations and notes
- The plan said the review batch carries only the root; it also carries the publisher, because a folder can hold a signed and an unsigned group and "exactly what the screen showed" needs both.
- A data drive's `Program Files` is treated as writable even where its permissions are tighter (the path cannot tell); the user can mark single programs.
- A defender heuristic blocked one of my own long inline shell scripts during this work (nothing ran); file edits were redone with the editor tools.

## Not built
- A "this folder" scope for patterns (F5): decided against, for the same reason as this slice. Patterns stay one-item-only.
- An application's own writable subfolder inside `Program Files` cannot be known from the path; documented in `docs/THREAT-MODEL.md`.
